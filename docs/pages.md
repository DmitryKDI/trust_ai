# Запуск с телефона через GitHub Pages

Workflow `.github/workflows/pages.yml` собирает `app/` из рабочей ветки
`main` и публикует только `app/dist`.
Исходные планы и локальные проекты в публикацию не включаются.

## Первое включение

1. В настройках `DmitryKDI/trust_ai` открыть **Settings → Pages**.
2. В **Build and deployment → Source** выбрать **GitHub Actions**.
3. Если у окружения `github-pages` ограничены ветки, разрешить рабочую ветку
   `main` (Settings → Environments → github-pages).
4. В Actions открыть **Publish planner to GitHub Pages** и запустить workflow
   для рабочей ветки. Если он еще не отображается, следующий push в `app/`,
   `config/` или сам workflow запускает публикацию автоматически.

Репозиторий приватный. GitHub Pages для приватного репозитория требует
GitHub Pro/Team/Enterprise; доступность тарифа здесь не установлена.
Публичная видимость репозитория этим workflow не изменяется.

Адрес после успешной публикации: `https://dmitrykdi.github.io/trust_ai/`.
До успешного deploy этот адрес не является подтвержденной работающей ссылкой.

## Повторная публикация

Изменения в `main` запускают сборку и проверку, затем публикацию при выполненных условиях GitHub Pages.
Сборка использует Node 24, `npm ci` и `npm run build -- --base=/trust_ai/`.
Базовый путь нужен также для файлов PDF и фоновых workers.
Перед публикацией workflow запускает тест собранного приложения на desktop
и touch/mobile: загрузка контрольного net15, распознавание семи зон,
три варианта мебели, отсутствие ошибок JS и адреса скомпилированных workers.
Изображения и проекты продолжают обрабатываться и храниться в браузере.

На телефоне открыть сайт в обычном браузере и загрузить план через «Загрузка».
Ручной контур доступен на шаге «Разметка» → «Помещение по точкам».
Для переноса проектов между устройствами нужен экспорт/импорт JSON.

Включение сайта не устраняет известные ошибки распознавания границ,
проемов и назначения комнат; см. `HANDOFF.md`.

## Исправление production workers и проверка

При подготовке запуска обнаружено: помощник `runWorker(url, ...)` скрывал
`new URL(...worker.ts, import.meta.url)` от Vite. Вместо сборки TS-worker
получался data URL с исходным TypeScript, и распознавание в production зависало.
Создание `new Worker(new URL(...), { type: 'module' })` перенесено в место
вызова, помощник получает готовый Worker. Так собираются оба пути
распознавания; алгоритмы геометрии не изменены.

Локально production-тесты прошли: 2 passed, 0 skipped, без ошибок JS.
Typecheck и сборка проходят. Векторный PDF как полный сценарий этим
JPG-тестом не проверяется; сборка его worker-файла проверена по output.

Воспроизведение из `app/`:

```bash
npm run build -- --base=/trust_ai/
npx playwright install chromium
npx playwright test --config=playwright.production.config.ts
```

При собственном браузере можно передать `PW_CHROMIUM=/path/to/chromium`.
